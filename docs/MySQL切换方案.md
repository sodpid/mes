## 3. 数据模型和 SQL 适配契约

| 当前实现 | MySQL 8.4 目标 |
| --- | --- |
| pg Pool/PoolClient、$1 参数 | mysql2/promise 连接池，显式 `?` 参数；将所有调用点适配，不做盲目的全局字符串替换 |
| pg rows/rowCount | 小型单引擎仓储辅助可统一返回 rows/rowCount，分别由 SELECT 行数及 ResultSetHeader.affectedRows 得出；不得以 truthy 对象代替实际影响行数 |
| uuid | CHAR(36) CHARACTER SET ascii COLLATE ascii_bin；服务端生成规范小写 UUID；所有 FK 两端类型/排序一致 |
| timestamptz | DATETIME(6)，统一 UTC；连接 session time_zone='+00:00'，禁止依赖服务器本地时区 |
| numeric(20,6) | DECIMAL(20,6)，mysql2 保留字符串，decimalNumbers=false；API 继续字符串 |
| jsonb 审计 | JSON；保留 JSON 结构及数值/布尔类型，不把对象二次编码成 JSON 字符串 |
| text[] 有限枚举 | 见下方固定集合决策，使用受约束 JSON 数组；API 仍返回数组 |
| ILIKE 与字符串拼接 `||` | 明确选用大小写不敏感搜索排序规则 + LIKE CONCAT('%',?,'%')；不能依赖 MySQL 默认库排序规则 |
| ANY(uuid[]) | 参数化 IN (?,...)，空集合显式产生 FALSE；不得拼接用户输入 |
| 默认供应方式 ANY(array) | JSON_CONTAINS(array, JSON_QUOTE(?)) 或对应 CHECK；严格区分 JSON 字符串与 SQL 字符串 |
| ::int、::text、interval '8 hours' | 显式 CAST 或在驱动结果归一化；DATE_ADD(UTC_TIMESTAMP(6),INTERVAL 8 HOUR) |
| LIKE companies INCLUDING ... | 每表显式完整 CREATE TABLE，外键/索引/CHECK 一并声明，包含原 002 的审计人员外键和索引 |
| PostgreSQL 错误码 | MySQL ER_DUP_ENTRY→409；FK引用/删除错误→409；CHECK、数据范围、非法枚举/日期→422；锁冲突有明确可重试错误，不暴露SQL或秘密 |

### 3.1 有限集合字段决策

供应能力、允许供应方式和生产策略都是固定最多2～3项的枚举值集合，不是独立业务实体。本次选择 JSON 数组以保留现有聚合/API，避免默认项与明细表外键的插入循环。该选择仅限这三个有限集合，不把物料策略、角色、授权等现有关系表合并成 JSON。

每个 JSON 列 NOT NULL，使用 MySQL8.4 支持的 `JSON_SCHEMA_VALID` CHECK，内嵌 schema 限定 type=array、items enum、uniqueItems=true；供应方式 minItems=1，另外两列是否非空按原条件控制。必须验证 JSON 标量、重复值、未知枚举均拒绝。默认供应方式须非 NULL 且 JSON_CONTAINS 成立；MAKE/SUBCONTRACT 存在时，生产集合非空且默认生产策略非 NULL 并属于集合。仅 BUY 可空生产策略。供应商角色存在时供应能力非空仍由事务内业务校验保证（跨表规则不能伪装成 CHECK）。

此为存储技术调整，不改变“采购/自制/委外可多选”及“订单/备货独立配置”的业务设计。若实现发现 JSON CHECK 在目标版本受限制，交回设计，不直接取消约束或改逗号字符串。

### 3.2 排序、日期与精度

普通文本用 utf8mb4。编码、用户名及权限枚举等相等/唯一判断显式使用大小写敏感且 NO PAD 的排序（建议 utf8mb4_0900_bin），保留 PG 的大小写敏感用户名行为；业务 code 仍先 trim+大写。避免改成默认 ai_ci 导致现有不同大小写用户名碰撞。中文名称搜索可以用 utf8mb4_0900_ai_ci，编码查询可直接规范化，但不能改变唯一键语义。

读取 DATETIME 用 dateStrings，业务/API 时间统一规范化为带 Z 的 ISO 字符串；不要让本地时区再次偏移。迁移导出时间用 PG UTC 文本保留微秒，导入 DATETIME(6) 不经 JS Date 截断到毫秒。原审计 JSON 内已有时间字符串保持原样。布尔列使用 TINYINT(1) + CHECK 0/1，驱动适配向 API 返回 boolean，不能使 React 把字符串“0”当 true。

DECIMAL 不经 Number；迁移比较用规范十进制字符串，最多6位小数，不因尾随零差异误判。保留严格 SQL mode，不用关闭严格校验来导入数据。账户密码哈希按原字符串复制。

## 4. 事务、锁与迁移执行器

业务事务使用同一 mysql2 connection 的 begin/commit/rollback，异常 finally 归还。保持 revision 条件更新、SELECT FOR UPDATE、审计及明细在同事务。推荐 session isolation READ COMMITTED，分类防环的读也必须受同公司串行锁保护。

PostgreSQL 事务级 advisory lock 不能直接映射为无释放的 GET_LOCK。本次采用单引擎具名锁辅助：同一专用连接 GET_LOCK(固定前缀+用途/公司UUID,有限超时)，检查返回值必须为1；最外层操作结束后在 commit/rollback 之后 finally RELEASE_LOCK，再归还池。连接故障时销毁连接，不能把仍持锁连接放回池。

- 分类创建/更新：在取得分类目标行锁和开始读取祖先前取得公司分类锁；所有路径顺序一致。不可在持有目标行后再等具名锁，避免与另一分类更新形成锁顺序倒置。
- 管理员修改：先取得实例内该数据库专属管理员锁，再读取并锁定用户，保护最后管理员。
- 仓库/库位：沿用统一先仓库后库位的锁顺序，保证最后有效库位约束。
- 迁移：数据库级专属锁，执行整个迁移序列期间持有；不能与其他项目共享模糊固定锁名。

MySQL DDL 隐式提交：**不能承诺多语句 schema 迁移失败可整体 rollback**。保留原 PG SQL 到归档目录，创建独立 MySQL migration 目录，校验和按新引擎重新记录。迁移执行器记录 APPLYING/APPLIED/FAILED、checksum及已执行步骤或明确失败位置，成功后标记 APPLIED；失败停止启动，不自动假成功或重放已应用脚本。首次创建的专属空目标可明确清理重建重试；对已有数据的库不得自动 drop。脚本拆分使用显式语句清单或可靠解析，不简单按分号切割含字符串/注释的 SQL。

## 5. 无损迁移和回退步骤

1. **先开发、后停写。** 准备 MySQL 架构、驱动、SQL、测试和工具，在隔离测试库验证；此时原 PG 应用可继续运行。保存切换前源码/构建产物、配置及 PG Compose 的可恢复副本或补丁，不能只保留数据库却丢失旧运行程序。
2. **预演。** 可只读导出当前 PG 在专属空 MySQL rehearsal 库演练；不得覆盖最终库或修改 PG。迁移工具使用明确源/目标，拒绝同目标重复导入非空业务表，不使用 upsert 去覆盖用户修改。
3. **最终冻结。** 识别并仅停止本项目18080应用进程，确认无本项目后台写入；不停止其他 Node/MySQL服务。迁移短时停机期间不开放新库写入。
4. **备份。** 对本项目 PG 做 pg_dump 自定义格式备份，检查退出码及 pg_restore --list 可读，计算文件哈希；保存全部表清单/行数与迁移前配置，备份位于忽略目录并不打印数据。原PG卷继续保留。临时导出含账号哈希/审计内容同样按敏感备份管理。
5. **一致导出。** 使用 PG REPEATABLE READ READ ONLY 同一快照导出所有业务表；列显式列举，按 FK 顺序导入 MySQL，分类按父子拓扑顺序。所有业务数据在单个 MySQL DML事务内写入，FK/CHECK保持开启；失败回滚，不靠关闭 FK 绕过错误。
6. **逐表核对。** 比较主键集合、行数、全部业务字段的规范化内容摘要；时间 UTC微秒、DECIMAL、JSON键顺序/数组、boolean做类型归一。密码哈希仅比较相等，不输出；全部关联无孤儿；检查默认策略集合、角色和审计数量。迁移生成仅含计数/哈希/差异字段名的报告。
7. **切换并验证。** 只有核对通过才改本项目 .env 为 MySQL并启动18080；原管理员密码继续有效，不重置、不seed。使用已有账号可用安全凭据验证时验证登录，否则验证哈希完全相等并用隔离测试账号验证认证链路，不擅自重置真实用户。确认原公司/物料/权限/审计可读；验证新写入、刷新、服务重启持久化，测试记录须明确并可清理，不改原业务资料。
8. **回退。** 尚未对外开放写入且切换验证失败时，停新应用、恢复旧构建/配置并指向保留PG恢复18080，保留MySQL现场。若MySQL已接收真实新业务写入，不直接回退到旧PG丢弃增量；再次冻结并先导出/协调增量回迁。不得用“恢复服务”掩盖数据丢失。

一次性迁移工具可在 tools/migration 或 scripts 专用路径使用 pg 开发依赖；正常应用、默认迁移及测试只用 mysql2。文档必须解释 pg 仅用于旧数据导入/回退验证，不宣称双数据库运行。历史PG迁移文件不可改写其已应用checksum。
