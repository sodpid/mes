# 工作中心管理实施契约

- 日期：2026-10-23；状态：已按本契约实施并验收上线；证据见[工作中心管理实施与验收记录](工作中心管理实施与验收记录.md)。
- 用户明确：添加工作中心管理，一个工作中心属于一个工厂，一个工厂可有多个工作中心（U-015）。其余字段和操作规则为本次最小实现设计，不冒充用户逐项指定。
- 实施使用当前已上线的公司/工厂/日历及改密版本为基线，当前镜像config前缀`4bb1d49f`，上线前核验完整身份。既有001、002迁移不得改写。

## 1. 范围与关系

公司 → 工厂 → 工作中心；每个工作中心必须且只能引用一个工厂，工厂允许零到多个工作中心。公司由工厂推导；工作中心是生产执行单元基础资料，可以代表加工单元或装配工位，不把整个工厂重复建成工作中心。

组织管理下增加“工作中心管理”，建议顺序公司、工厂、工作中心、工作日历。工厂详情和列表增加工作中心快捷入口，进入时携带工厂筛选。保留原七模块目标，尚未建设的部门/员工/班组/岗位仍不建空壳。

本批不实现设备、工序执行、产能、班次排班、人员负责人、车间或委外供应商关系。旧《主数据模块详细设计》中的 INTERNAL/EXTERNAL、workshop_id、supplier_id 属于后续生产能力设计；本批只建通用工作中心，不给缺字段的现有记录暗示“已支持委外”。后续增加类型时用显式迁移和业务配置补齐，不影响本次稳定ID。

工作中心默认使用所属工厂的工作日历，不复制日历表、不允许工作中心覆盖；详情显示“使用工厂工作日历”及入口，跳转现有工厂日历页面。日历缺失时显示未配置，不能当作全工作；无需额外建立重复的工作中心日历解析API。

## 2. 数据字段与迁移

新增 `db/mysql/003_work_centers.json`，若实施时编号已占用则顺延。创建 `work_centers`，使用与现表一致的 UUID、字符集/编码排序规则和通用审计字段。

| 字段 | 必填与规则 |
| --- | --- |
| id | 服务端UUID，稳定主键 |
| company_id | 非空，服务端从工厂取得；不可由请求伪造 |
| factory_id | 非空，必须是有权限且有效的工厂；创建后固定，草稿也不可直接转厂 |
| code | 1～64，沿用去首尾空格、转大写、`A-Z0-9_.-`；工厂内唯一，停用编码不复用 |
| name | 1～200，去首尾空格，允许重名 |
| remark | 可空，最多2000字，用于职责/说明，无独立重复description字段 |
| status | DRAFT/ACTIVE/INACTIVE，初始DRAFT |
| revision | 正整数初始1，变更含状态须校验旧revision |
| created_at/by、updated_at/by | UTC DATETIME(6)、操作账号FK；服务端设置 |

约束：`UNIQUE(factory_id,code)`；`UNIQUE(id,company_id,factory_id)`供未来工艺引用；复合外键`(factory_id,company_id) → factories(id,company_id)`；操作人引用users；全部RESTRICT；索引`(company_id,factory_id,status)`。公司不需要独立冗余FK才能保证一致，但可按现表风格增加。不新增默认数据，不改现公司工厂ID、账号密码或现日历数据。

归属创建后固定可最大程度复用现通用资料规则。录错工厂时删除未引用草稿后重建；已启用需停用旧记录并在目标厂新建，未来生产引用不允许因普通编辑而跨厂迁移。启用后编码不可修改，名称说明可按规则修改。

## 3. 生命周期与父级规则

- 草稿可编辑、启用、删除未引用草稿；已启用/已停用不可物理删除，停用后可重新启用；草稿不能直接停用。
- 新建、编辑、启用均要求公司和工厂有效。父级停用后仍可查询工作中心及历史审计，但不得编辑或新增业务使用；允许工作中心停用以及删除未引用草稿。此限制明确作用于新增工作中心模块，不顺带改变其他旧主数据行为。
- 工厂/公司停用沿现规则：不批量改子记录status、不因存在工作中心就一律禁止停用；界面停用确认呈现有权限的工作中心引用数量。有效性为工作中心、工厂、公司三层均ACTIVE。重新启用工厂后，原本ACTIVE工作中心自然恢复有效，界面应说明。
- 公司/工厂删除引用检查纳入工作中心，任何工作中心（包括草稿）存在时不得删除所属工厂；FK作为后盾。不擅自级联删除。
- 尚无工艺路线/生产单据实际引用，本批references准确显示“生产工艺及业务引用尚未接入”，不伪造已核查订单为0。后续新建路线/任务时使用含公司工厂的复合引用和有效性检查。

## 4. API、事务与权限

沿用 `/api/v1`、标准详情/分页格式、中文错误、Origin保护、输入白名单及通用审计。可扩展现 master.ts 实体白名单和通用页面，但必须逐一适配列表范围过滤、实体到表名映射、状态有效性、引用统计与前端字段。

| 接口 | 合约 |
| --- | --- |
| GET /work-centers | search、company_id、factory_id、status、activeOnly、page/pageSize、排序白名单；默认包括草稿停用 |
| POST /work-centers | code、name、factory_id、remark；服务推导company_id，若兼容通用表单允许传company_id，则不一致须422，绝不信任传值 |
| GET /work-centers/:id | 详情含公司/工厂及有效性原因、revision、使用工厂日历说明 |
| PUT /work-centers/:id | revision必填，仅修改允许字段；传入不同公司/工厂拒绝，不静默忽略 |
| POST /work-centers/:id/activate、deactivate | revision、reason必填；完整状态/父级检查 |
| DELETE /work-centers/:id | revision；仅未引用草稿 |
| GET /work-centers/:id/references、audit | 对象与数据范围授权后返回；审计沿用现主数据授权，而非另扩大权限 |

ADMIN全权；EDITOR在授权范围新建/修改/删草稿；RELEASER在授权范围启停；VIEWER只读。非ADMIN必须同时具备公司和工厂范围；无权单对象详情/修改/审计/引用统一404，角色不符403。列表自动过滤，不能通过伪造company_id、工厂筛选、快捷入口或字典绕过。跨公司厂关联、父级无效422；重复/并发/引用409。

创建和修改遵守统一锁顺序`company → factory → work_center`，先根据已有对象定位归属并校验可见性，再取得锁并重新检查父级状态与revision；工厂与公司既有状态写路径使用同样顺序，防止父级停用和工作中心编辑并发漏检。所有修改、状态、revision与审计同事务。UPDATE条件带revision或行锁后严格比较；同revision两次并发只有一个成功。

新增 company/factory 引用统计只返回用户有权工厂的工作中心数量。删除保护使用全量实际引用，不依赖被过滤的显示数量。新增工厂detail工作中心计数也需在已校验该工厂可见的前提下执行。审计记新增、前后字段、状态、删除和原因，不含密码、哈希或会话令牌。

## 5. 页面操作

列表：公司、工厂、状态筛选，编码/名称搜索，分页；列为编码、名称、公司、工厂、状态、有效性、操作。新建表单公司用于缩小工厂选择，实际所属公司由工厂决定；显示编码、名称、所属工厂、说明。选择器只给有权限且有效工厂；详情可显示后来停用的原归属，不能因过滤丢失历史名称。

编辑固定公司工厂，启用后固定编码；父级停用显示明确只读原因，后端仍校验。详情展示引用、审计及工厂日历跳转。停用/删除弹窗展示影响和状态规则，启停原因必填；409提示刷新，不无条件覆盖。维护按钮按角色显示，启用还需父级有效。加载/空状态/失败重试中文可用。

快捷入口只改变筛选和导航，不自动创建中心或年度日历。用户可在同厂创建WC01/WC02，在另厂重用WC01；列表与选择器显示工厂避免歧义。

## 6. 验收与上线

1. 真实MySQL003迁移成功，旧001/002 checksum不变；新增表初始为空，既有公司、工厂、日历、账号及密码审计数据不被覆盖。
2. UI建立C01/F01下WC01、WC02，另厂F02允许WC01；同厂大小写/空格规范化重复拒绝。草稿修改/启用/停用/恢复/删除规则均通过。
3. 缺factory、跨公司伪造、创建后转厂、父停用编辑/启用均拒绝；父停用历史可查，工厂引用检查包含工作中心；父停用与编辑并发保持一致。
4. 无权用户不能读写跨厂记录、字典/引用/审计；VIEWER写入403，EDITOR启停403，RELEASER普通编辑403；同公司但未授权工厂仍不可访问。
5. 同revision并发只有一次成功；审计与主体同事务，失败不留下半条修改；未来生产引用明确未接入。工厂日历跳转打开同厂数据且不新建重复日历。
6. 浏览器实际新建、编辑、状态切换、工厂快捷筛选、错误提示及刷新持久化；回归日历核心场景和本人改密，不重置用户密码、不回显凭据。构建与必要测试证据记录后再更新U-015完成状态。

用户已授权按既定流程实施上线。上线采用已验证的增量迁移流程：新镜像基于当前含日历及改密版本；备份，短暂停止仅MES app，保存当前业务表一致快照，解锁仅MES迁移账号执行003，再重锁，核对原表原列，启动新app并验证后切current。当前已有日历三表，**不得直接复用硬编码仅17业务表、只接受旧表集合的首次上线export工具**；快照校验应包含当前全部业务表和已应用迁移状态，003新增表单独核验，凭据内容不输出。

MySQL DDL不可假设事务回滚，迁移失败保持步骤记录并检查。失败回退当前含日历/改密的上一应用镜像和current软链，保留新增表及数据，不恢复旧数据库覆盖新写入；回退应用不理解工作中心引用，冻结公司/工厂删除以避免兼容期语义不一致。验证健康后才设发布完成标记；EXIT负责重锁并在失败时恢复旧MES应用，不操作其他站点或共享MySQL服务。
