# 主键与UUID配对校验迁移方案

日期：2026-10-24。状态：当前实施契约，未实施验收。关联U-017。

> 本版完全替代此前“公开UUID路由、public_id唯一索引、保持旧API id语义”的草稿。用户最新明确：查询传自增id，UUID作为必需校验参数，不用UUID查询、不为其建立索引。本次前后端同步切换，不维持旧UUID-id API。

## 1. 决策与安全边界

实体采用 `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` 与 `uuid CHAR(36) CHARACTER SET ascii COLLATE ascii_bin NOT NULL`。原UUID完整保留到uuid，新实体生成UUIDv4。uuid不建普通/唯一/复合索引；id主键已保证(id,uuid)配对唯一。不同实体甚至意外同UUID不影响按主键定位；不依赖UUID全局唯一做关系。

查询只按数字主键id定位，应用取到行后精确比较uuid，再按原角色和组织范围授权。不存在、UUID不匹配、无数据权限统一404，不泄漏哪个检查失败；缺少/格式错误配对参数可统一422。UUID是难猜的配对参数，不是授权令牌；拿到pair、重放请求也不能越权。不得以uuid WHERE定位，亦不得建立uuid→id运行期缓存绕开此规则。业务code、号码、幂等键、session token等独立业务唯一索引不能因此删除。

所有API数字ID都是十进制字符串，不通过JS Number。正常展示仍用业务code/name。列表在既有授权过滤后返回id+uuid；保护不能靠隐藏列表实现。API日志脱敏UUID header及body，不打印密码、session、数据快照正文。

## 2. 全部25表与字段分类

以下17表原id UUID转为uuid，新增内部数字自增id：users、companies、factories、partners、warehouses、locations、units、material_categories、materials、material_factory_policies、audit_logs、factory_calendars、calendar_week_patterns、work_centers、numbering_rules、numbering_counters、number_allocations。

其原真实实体引用全部改为BIGINT UNSIGNED，保持NULL语义：company_id→companies，factory_id→factories，created_by/updated_by/actor_id/user_id→users，warehouse_id→warehouses，custodian_supplier_id/preferred_supplier_id→partners，category_id/parent_id→material_categories，base_unit_id/unit_id→units，material_id→materials，policy_id→material_factory_policies，calendar_id→factory_calendars，rule_id→numbering_rules，allocation_id→number_allocations。以表级显式映射确定目标，不能按后缀盲替。

余下8表不增加假自增id：sessions保留token_hash主键、user_id改数字；partner_roles(partner_id,role)、material_units(material_id,unit_id)、material_inspection_policies(policy_id,inspection_type)、user_company_scopes(user_id,company_id)、user_factory_scopes(user_id,factory_id)、calendar_exceptions(calendar_id,date)、number_allocation_items(allocation_id,ordinal)继续复合PK，实体引用改数字。

所有原业务unique、复合FK、RESTRICT、状态/范围CHECK必须保持，尤其公司工厂一致、年度唯一、同公司供应商/分类、号码公司用途唯一。父子/关联表通过父资源pair授权访问，枚举/日期/ordinal自身不是独立实体，不增加uuid。17表uuid均不作为任何索引的一部分；迁移校验其与源UUID逐行一致，不假设或新增全局唯一约束。

### 特殊字段不能机械转换

- sessions.token_hash保持原值及索引；expires_at和用户关联保留，不通过清空会话简化迁移。
- 审计对象可能已删除：新audit_logs同时存entity_id BIGINT NULL及entity_uuid CHAR36、company_id/factory_id数字可空及company_uuid/factory_uuid历史UUID可空。现存对象/组织由映射填数字，已删对象数字NULL、UUID仍保留。actor_id是真FK必须映射。只索引数字entity_id及组织ID，历史uuid不建索引、不以其查询。旧多态entity_type由显式实体注册表解析，未知或历史非实体类型保留UUID和NULL数字，不伪造对象。
- 旧before_json/after_json完全保留，新增snapshot_version=1标记旧UUID字段语义；新审计snapshot_version=2，写公开id+uuid DTO。页面标明历史快照，不能把旧JSON的id UUID作为新数字id发送；跳转只用经服务补充的现存对象pair。无现存组织映射的旧审计仅ADMIN可查，不能因NULL扩大普通用户权限。
- 编号scope_key原C或F:<原工厂UUID>是稳定业务命名空间，原样保留，不能改F:数字重启计数。计数器current_value、period_key、已发号码不变。新工厂规则用已按id定位校验的factory.uuid构造scope_key，无UUID查表。原scope_key拼factory_id CHECK调整为范围形状校验；应用检查完整scope_key匹配所选工厂uuid，数字复合FK保证公司工厂一致。
- number_allocations.business_id当前是未来业务对象的UUID幂等键，并非现有25表实体FK；保持其值与业务唯一约束，不为了“uuid无索引”删除该防重复业务索引。新增生产实体未来再明确内部business_row_id，不在本批创造生产表。rule_snapshot原UUID字段、fingerprint完整保留，旧快照在响应标注版本1；新快照版本2提供id+uuid配对，同时保留取号canonical计算的旧UUID语义。
- 内部allocator无HTTP入口。本次请求规则/组织引用改可信数字+uuid refs，入口按主键验证pair及业务授权；fingerprint仍由已验证行的原uuid生成原canonical字段，字段顺序/内容不变，使迁移前同key重试仍命中原号。business_id继续原UUID业务键、requestTime冻结、业务digest及数量不变；不接受客户端自授业务权限。现有生产是否非空必须现场核验，即使空也以非空夹具证明兼容，不跳过此规则。

## 3. API与前端统一配对契约

认证例外：登录按用户名/密码，不要求客户端事先知道id+uuid；auth/me、退出、本人改密由已验证session确定当前用户，不接受客户端另传目标用户pair。仍要求API版本2及原身份/口令校验。管理员操作其他用户必须目标pair。未指定实体ID的集合查询无需pair；不可借这些例外新增任意id直查接口。

1. 单实体GET/PUT/DELETE/activate/deactivate及其子操作路径 `/.../:id` 改数字字符串；必需header `X-Resource-UUID`。GET不使用body，不把UUID塞URL日志。服务只按id SELECT；配对检查与权限检查在业务锁定事务内完成。格式校验为正十进制、不带前导零、范围<=18446744073709551615。旧UUID路径返回稳定的API版本不匹配/参数错误提示，不回退UUID查找。
2. POST/PUT body所有实体引用成对：company_id/company_uuid、factory_id/factory_uuid、parent_id/parent_uuid、unit_id/unit_uuid等；可选引用要么两字段都省略，要么两者都null，要么完整pair。更新只改名称时可省略不变引用；若传了id即必须传uuid，即使id未变。多余孤立uuid或孤立id拒绝。created_by等由服务产生，客户端不可传。
3. 集合筛选涉及实体id也必须配对，过滤id留在query，所有对应uuid放 `X-Reference-UUIDs` header JSON（静态白名单键如company_id、factory_id、rule_id；限制长度及数量）。query无id但header有相应uuid也拒绝。先按id验证pair及范围再筛选；禁止仅因筛选结果为空跳过pair验证。无资源筛选的列表不需要pair，仍按登录权限过滤。日历工厂日期解析接口也遵守factory_id+header映射。
4. 批量实体操作统一items:[{id,uuid,...}]，逐项验证，数量有上限，同批任何错配按现事务原子拒绝。用户公司/工厂授权数组改company_refs/factory_refs:[{id,uuid}]；物料单位/工厂策略等嵌套实体引用使用其对应_id/_uuid对，表内枚举键不加uuid。
5. 所有返回DTO显式序列化：实体id+uuid，关联引用id+对应_uuid；用户auth/me公开组织refs与数字字符串id，禁止将内部Actor直接返回。对已授权主体的关联对象按既有权限规则返回/裁剪，不能由新增uuid字段泄漏未授权关系。审计、分配头/明细、规则、日历周规则、references接口及嵌套factoryPolicies全部覆盖。
6. 客户端集中API层从当前选中实体保存pair并发送header；Select值只存数字字符串但选项保留uuid，禁止从展示code猜uuid。刷新后重新从授权列表取pair。页面路由若只含数字id、内存无uuid，不自动单查id补uuid；从有权集合重新定位/选择，或显示返回列表重新打开。不得为恢复旧深链接新增免uuid详情入口。
7. 新API发布契约版本2；前端每请求发送 `X-MES-API-Version: 2`，旧缓存SPA缺失/旧版本请求统一426或明确稳定错误并提示整页刷新，尤其写请求在任何修改前拒绝。新页面HTML no-cache、静态资源hash，原子发布新前后端。版本检查对健康/静态资源等按明确白名单放行；旧登录不能绕过创建会话写入门禁。CORS如存在则明确允许配对与版本headers，不扩大origin。
8. mysql2数字主键读取启用supportBigNumbers/bigNumberStrings；内部也统一字符串，insertId不得不安全转Number。INSERT省略数字id；同连接LAST_INSERT_ID转CHAR读回。实体uuid不能按WHERE查询来读回。统一静态映射模块/DTO层，不做全局SQL字符串替换、任意JSON转换或逐字段N+1查库。

## 4. 迁移系谱与影子库

当前代码为NUMBERING25（001～004），部署记录最新编号版config6f397d36…；这不是本轮现场证据，Sol必须核验现current/config、完整checksum、25表及实际行数，不沿用旧83行。

采用MES专属影子数据库，例如精确配置 `mes_bigint_<release>`，不在原mes逐表ALTER。旧db/mysql/001～004及checksum保持；新目录 `db/mysql-bigint/001_bigint_uuid_baseline.json` 明确全25表。新schema_migrations只记录真实执行的新baseline，不伪造旧迁移已运行。新runtime启动校验新系谱/关键结构，连旧库fail closed。本次不添加假005，不保双SQL运行分支。

目标先执行DDL，MySQL DDL失败标FAILED，不宣称事务回滚。目标空且准确schema通过后，在DML事务中导入。映射键为(表,旧UUID)→数字字符串，稳定排序预分配正整数并显式导入，自增位置核验大于MAX(id)。FK保持开启，分类拓扑和其他依赖顺序导入。真实FK缺映射立即停止；历史审计例外按前述处理。已非空/未知schema/checksum目标拒导入，不自动删原库；失败专属目标由执行者明确核对后重建。

转换保留全部用户名/password_hash/角色/session有效期/权限、NULL、微秒日期、DECIMAL、JSON语义、revision、状态、日历历史锁、业务码和计数/号码；不seed、不导入本地业务、不生成生产测试号、不删审计。反映射验证将新数字ID/FK还原旧UUID，历史JSON原样，对所有原字段逐表全量逻辑摘要相等；新增数字列/版本列另验证规则，不仅比较行数。映射文件/快照0600，报告只输出数量/摘要/结构结果。

## 5. 备份、切换与回退边界

工具明确区分旧NUMBERING25和新BIGINT_UUID25，不能只看25表。完整检查列类型/空值/PK/unique/FK/CHECK强制及条件/collation/表全集/迁移checksum；新uuid不得有索引。旧导出工具固定旧镜像保存，新export/import只同新系谱，跨系谱为专用转换命令。恢复保留数字id、uuid及自增位置。旧/新备份分标签，发布后备份脚本实际目标必须切新库，不能继续只备份冻结旧mes。

发布步骤：

1. 先通过隔离完整转换、API/浏览器回归及非空新库恢复演练，准备专属库、最小权限运行和迁移账号。共享MySQL/别的库/站点不变。
2. 完整SQL备份；仅停止MES应用及所有MES写入者，确认无写连接，冻结后导出最终快照。旧运行账号禁写/锁定并核验。转换必须使用最后冻结快照。
3. 转换影子库，验25表全字段反映射摘要、无孤儿、pair稳定、结构和AUTO_INCREMENT；专用迁移账号重锁。只在隔离监听/网络以只读权限启动候选验证，不提前接收公网写入。旧配置、旧镜像、旧库保留。
4. 正式开放写入前失败可恢复旧账号权限/旧镜像/旧配置/current，原库数据未改；恢复失败明确报警非零退出，不吞错误。
5. 在任何正式新写入可能发生前持久化发布状态 `WRITES_MAY_HAVE_STARTED`，然后同时切新应用及新数据库配置。此后EXIT禁止自动切回旧库；即使新启动/健康失败也应停止MES、报警并前向修复。回旧系谱须另行冻结新写入、完整导出并验证逆转换，不能以旧备份覆盖增量，不凭肉眼“没看到请求”判断可退。
6. 健康及权限/配对只读验收后完成；新库全备份并演练恢复。旧库只读保留，本轮不立即删除。旧镜像不接新库，新镜像不接旧库，旧SPA的写请求受版本门禁拒绝。

## 6. 验收与实施顺序

- 17实体数字自增、uuid无索引；8复合/认证表合理；真实FK全部数字且类型一致；业务unique不丢。公开列表pair、详情及每个读写/引用/筛选/批量接口严格要求pair；错误uuid、数字越权、孤立uuid、空配对、旧API版本全部无写且无信息oracle。
- ID超过2^53的隔离样本全流程精确；同表并发自增、UUID校验正确；不同表同数字id不串对象。同uuid不同实体/不同id不因任何隐藏UUID定位发生混淆。
- 现有API和五浏览器场景同步升级配对契约并全回归；旧账号密码、session、改密撤销、范围变更/角色仍正确，不以重置密码或清会话通过测试。旧SPA提示刷新，不偷偷用旧UUID字段当数字。
- 历史JSON/已删对象审计可解释且无UUID查找；新审计pair版本2正确；编号旧key跨迁移命中、scope稳定、计数续号和业务事务回滚/权限保持。现场为空仍使用非空夹具（含分配记录）验证。
- 源快照→影子转换逐字段逻辑相等，新库导出→空库恢复逐原新字段摘要相等，自增继续正确；未知表/错误schema/缺映射拒绝。模拟切换前失败恢复及写入后失败禁止自动倒库。

Sol建议按顺序完成：新schema/类型/显式pair解析与DTO；公司工厂及认证纵向链路；剩余实体与日历/编号/审计；统一前端API版本/pair与所有页面；转换/备份工具及非空演练；全回归；影子发布。强耦合数据访问与DTO由单一负责人负责，独立测试或静态审查可以分工，不多人修改同文件。所有设计中尚未完成项不能写成已上线。
