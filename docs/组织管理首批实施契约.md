## 2. 日历规则与边界

1. 工厂每年唯一日历（factory_id,year），year 允许 2000～2100；新建表单明确选择工厂、年份、每周工作日，建议预填周一至周五但可在保存前改成六天/七天或任意集合。API 必须收到工作日集合，不在后台默默用双休。允许全周休息并提示，不强行认定错误。
2. 日历按工厂当地自然日计算；日期以 YYYY-MM-DD/DATE 传输存储，不经浏览器 UTC 转换。审计使用 UTC。闰年使用真实公历校验，禁止 JS 自动把 2 月 30 日归一化成 3 月。
3. 周规则按生效日期分段，首段从 1 月 1 日开始，最后覆盖至下一年 1 月 1 日（不包含）。每段七个工作/休息标志；区间无重叠、无空缺。可在未来某日切换工作周，旧日期不变。
4. 日期例外为 WORK 或 REST，含可选 note（最多 500 字）。同日期唯一；日结果=该日例外优先，否则周规则。恢复默认删除例外，重新继承该日周规则。备注仅文本，不驱动逻辑。
5. 日历状态 DRAFT/ACTIVE/INACTIVE；草稿可配置年度任意日期，启用后工作规则及例外仅能修改工厂当地今天及以后。已启用日历后来停用仍保留历史锁定，不以重新启用/停用绕过；首版不提供历史纠错接口。可用 `activated_at` 标记曾启用。
6. 首次建立当前年日历允许定义全年基线，界面说明“首次配置，非历史排班记录”；过去年度可建立草稿供查看，但不得启用已结束年度。既有过去年度的已启用日历继续可读，不自动停用。
7. ACTIVE 日历允许有维护权限者修改今天/未来日期并审计，不另做发布版本工作流；改动增加 revision。它仅是工厂工作日期规则，不宣称已同步任何排班。页面固定提示“班次及班组排班尚未接入”。
8. 工厂或公司未启用时允许读取历史日历、审计和禁用原因；禁止日历新建、规则修改、启用。允许有状态权限者停用日历；允许删除未启用且未引用草稿。父级停用不批量改子日历状态，effective_active 同时检查三层。
9. 缺日历、草稿、停用、父级停用的日期查询都明确返回未配置/不可用及原因，不默认全工作/全休息。维护详情仍能预览其配置结果，但注明不可用于业务。
10. 不自动导入法定节假日，不把节日文字当休息标志。复制年份非首批必需，完成核心后可仅复制工作周，不复制/平移节日例外。

## 3. 最小数据库增量

新增顺序迁移 `db/mysql/002_factory_calendars.json`（实际若占号则顺延），与当前 JSON statements 迁移器兼容。保留原迁移 checksum。

| 表/变更 | 必须字段与约束 |
| --- | --- |
| factories 增列 | timezone VARCHAR(64) NOT NULL DEFAULT 'Asia/Shanghai'；服务校验合法 IANA |
| factory_calendars | id UUID、company_id、factory_id、year、status、revision、remark、activated_at nullable、created_at/by、updated_at/by；UNIQUE(factory_id,year)；(factory_id,company_id)复合外键到现工厂，操作人外键到 users |
| calendar_week_patterns | id、calendar_id、valid_from、valid_to、work_days JSON（1=周一…7=周日，唯一整数集合，可空）；FK calendar，索引(calendar_id,valid_from)，CHECK 日期顺序和JSON合法结构；完整覆盖由服务检查 |
| calendar_exceptions | calendar_id、date、day_type WORK/REST、note；PRIMARY KEY(calendar_id,date)，FK calendar；日期属于年度由服务检查 |

复用现有 audit_logs，不另建个人信息表。无必要给日历增加 code/name；列表以“工厂名称 · 年份”显示，避免被通用 CRUD 强迫造无意义编码。主表及明细同一事务保存，禁止明细各自提交。所有删除 RESTRICT；删除未引用草稿时显式同事务删除自有明细，再删除日历，保留审计。

补充现公司/工厂引用统计对日历的引用（公司级统计亦须按用户工厂权限过滤）；防止有日历的工厂被删除。既有公司/工厂启停用语义保持兼容，新增日历有效性检查承担父级停用传播。

## 4. 接口契约

沿用 `/api/v1`、中文错误、现有 cookie/Origin 校验、JSON schema 白名单和受保护事务。公司/工厂旧路径不变。新增日历独立服务，不把其 parent_id/时间规则塞入现物料分类有效性函数。

| 方法/路径 | 请求及结果 |
| --- | --- |
| GET /factory-calendars | company_id/factory_id/year/status、分页；只列有权限工厂；items/total/page/pageSize 与现接口一致 |
| POST /factory-calendars | factory_id、year、workDays 必传、remark 可选；服务推导 company_id，建立草稿和首段全年规则；201 |
| GET /factory-calendars/:id | 主表、revision、周规则、日期例外、effective_active/reasons、当地 today、history_locked_before；返回详情格式与现工程一致 |
| PUT /factory-calendars/:id/rules | revision、reason 必填；可选 weekPatterns 完整有效区间数组、changes 日期操作数组、remark；changes 每项 date、operation=WORK/REST/RESET、note；重复日期拒绝，最多366项；部分字段未提供不覆盖 |
| POST /factory-calendars/:id/activate 或 deactivate | revision、reason；状态权限、父级有效性和完整规则检查；首次启用写 activated_at |
| DELETE /factory-calendars/:id | revision；仅未曾启用的未引用草稿；409拒绝冲突 |
| GET /factory-calendars/:id/audit 或 references | 继承现审计/引用授权语义；references 明示排班尚未接入，不伪造已检查0条排班 |
| GET /factories/:id/work-calendar?from=YYYY-MM-DD&to=YYYY-MM-DD | 两端包含，最多366天，可跨年；逐日 date、availability、is_working（不可用为null）、source=WEEK/EXCEPTION或null、note、calendar_id/revision；缺年份的日期明确UNCONFIGURED，其他已配置日期仍可返回 |

规则接口先锁所属工厂行、日历行，在同一事务内校验父级状态和 revision、载入旧规则、计算变更后全部规则、校验历史区间和明细、写入与审计。父级公司启停应兼容锁顺序：涉及父级状态的操作统一 company→factory→calendar；避免日历保存与父级停用交错导致保存漏检。改变已锁历史的日期语义或其例外备注一律拒绝，不只比较最终工作/休息值；周规则前缀语义及有效边界也不得改写过去。

revision 用条件更新/行锁校验，失配409；同厂同年竞争建立由唯一键兜底并映射409。批量中任何日期无效、越年、历史限制、越权或父级失效，全部不写，包括备注、revision和审计。404屏蔽不存在/不可见；403角色不足；422日期/规则业务错误。严禁回显SQL、哈希、会话令牌。

## 5. 本批角色矩阵

不增加角色引擎，不改任何现用户授权。公司/工厂既有角色行为保持：公司仅ADMIN写；工厂ADMIN/EDITOR维护、ADMIN/RELEASER启停，所有读取仍按现范围。

日历沿用工厂角色约定：ADMIN全权；EDITOR在有公司+工厂权限内新建、编辑和删除草稿；RELEASER在授权范围启停；VIEWER只读；各非ADMIN需同时具备公司及工厂授权。日历审计遵循既有审计接口的限制（当前主数据审计若仅ADMIN，则日历同样仅ADMIN）。下拉选项、列表、详情、年度查询、引用统计都做服务端范围校验，前端隐藏按钮不是安全边界。此矩阵是为复用当前角色的本批设计，覆盖完整方案对新增功能默认仅管理员写的泛化建议，不涉及尚未实施的员工权限。

## 6. 前端操作闭环

工作日历页面：公司→工厂→年份筛选、状态和未配置提示；未配置可新建。新建对话框明确工作周选择。进入日历后显示月历、上一月/下一月/今天、年度选择、周规则设置、工作/休息/补班图例和已选日期数。

点击单日或多选日期（另提供日期范围及星期筛选即可，无需拖拽库）→选择设为休息、设为工作或恢复默认→填备注及变更原因→本地显示变更预览→保存API重新校验。预览不必单独新建接口；须清楚显示受影响日期和当前/目标类型。恢复默认后显示周规则来源。周规则改动需选择生效日并显示受影响日期范围；草稿可改全年，曾启用日历只能今天或未来开始。

过去日期禁用编辑，仍可查看来源和备注；同年度非当前月不丢已选状态或明确清空。保存成功重新查询服务端数据；409保留未保存输入，提示刷新比对；取消不保存。状态/角色禁用按钮并说明原因。批量删除例外使用RESET，不物理删除日历。工厂页可快捷进入其当年日历；公司工厂详情仍可用。

## 7. 验证与交付标准

在独立 MySQL 测试库验证，保留既有改密测试和主数据回归；不得清理用户库。必须覆盖：

- 公司工厂 CRUD、编码唯一、草稿删除/引用拒绝、状态与父级有效性、角色/范围、审计和revision；原物料仓储及本人改密仍可用。
- 不同工厂同年可建，同工厂同年重复/并发拒绝；伪造公司或无权工厂的列表/详情/日期查询/修改均拒绝。
- 周规则+REST/WORK例外优先；RESET继承；批量内一条错误全部回滚；并发相同revision只有一次成功；审计有前后差异和原因且无秘密。
- 2028-02-29有效、2027-02-29无效；12月31日至次年1月1日跨年解析、缺年配置、日期范围限额；按工厂时区确定历史边界，不用服务器/浏览器时区偷换。
- 周规则年中变更、过去日期锁定、停用再启用不能绕历史锁；父级停用后历史可读、规则不能改、日历不能启用；停用日历对业务日期查询不可用。
- 浏览器真实新建一套工厂日历，修改工作周、单日休息、周末补班、批量设置、恢复默认、备注保存后刷新仍存在；日历翻月、权限按钮、冲突/错误可见。记录截图或实测结果，不只测API。

交付报告列出变更文件、迁移、构建/测试结果、本地使用入口与剩余四组织模块。需求基线只在有验收证据时更新完成状态。此实施任务本身不新增外部消息、生产发布或提交推送授权。
